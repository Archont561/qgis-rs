# Session lifecycle for qgis-rs

A session is a loop with five phases, and this file sequences all of them: **(1)** confirm the
environment, **(2)** survey the backlog, **(3)** propose the session and stop, **(4)** work the
tasks under the house rules, **(5)** after the work lands on `main`, report and hand the next
session its opening prompt. The four artifacts those phases produce have templates in
[`standup-template.md`](standup-template.md), cited below as *template §1* … *template §4*.

Two rules span the whole loop. Never propose work you cannot execute — an environment that is down
changes what is possible. And never close on an unproven claim: the proof this machine cannot
produce is an open item, not a checked box.

## 1. Confirm the environment (pixi only)

The repository has **two** pixi environments and both are already materialized in a codespace:
`default` (Rust, C++ toolchain, QGIS) and `bun` (the JS/TS workspace). Check before you build —
a fresh clone with no `.pixi/envs/` needs `scripts/restore.sh`, an existing one does not:

```bash
ls -d .pixi/envs/default .pixi/envs/bun
# both missing (an airlocked machine, or a fresh clone):
bash scripts/restore.sh   # generated; reads branch/pundle/platform out of pixi-sandbox.toml
```

`scripts/restore.sh` is generated by `pixi sandbox init --project-root . --script-path
scripts/restore.sh`. The published branch is `sandbox/developer-linux-64` (bundle `developer`,
environments `default` + `bun`, platform `linux-64`, from `pixi-sandbox.toml`); it is repacked by
the generated `publish-sandbox.yml` on every push to `main` that touches a sandbox input, so after
a merge `gh run list` — or the Actions tab — shows a `publish sandbox` run. Override the ref with
`PIXI_SANDBOX_BRANCH`, or disambiguate bundles with `PIXI_SANDBOX_BUNDLE`.

### This devcontainer has network; the airlock does not

That distinction changes which commands are legal, so state it rather than assuming:

- **Here**: conda-forge, crates.io and github.com all answer. `pixi lock`, `pixi run xtask`,
  `cargo` fetching crates and `bun install` all work normally. Prefer `pixi run` for anything that
  needs packages, but `--frozen` is not required and is not the house convention.
- **On an airlocked machine**: crates.io, prefix.dev and static.rust-lang.org do not answer, so
  cargo needs `--offline` against the vendor tree and pixi needs `--frozen`.

### Every repo task goes through the pixi binary

`pixi run xtask <subcommand>` is **the** entry point ([D10](/.knowledge/decisions/D10-xtask-over-shell-scripts.md)).
Repository automation is a Rust subcommand, never a `scripts/*.sh` file.

```bash
pixi run xtask <sub>            # ci, check-cpp, lint-toml, check-sources, scaffold, release …
pixi run gates                  # ci without the coverage producers — the fast pre-push loop
pixi run ci                     # the full gate, identical to ci.yml
pixi run format-cpp             # write; the gate uses check-cpp (diff mode)
pixi run clang-tidy             # discovers its own include paths — see D10
pixi run setup                  # link libqca under the Qt5 soname QGIS still asks for
pixi run -- cargo <cmd> -p <crate>
pixi run -- bun --filter=<pkg> run <script>     # per-package verbs, one line each in package.json
pixi run -- bun x turbo run <task>              # repo-wide JS fan-out
pixi run backlog task list --plain
pixi run -- lefthook install                    # fresh clone only
```

Two `pixi` facts that bite:

- `cargo` is **not** on `PATH` in a bare shell here. A plain `cargo test` fails with
  `Permission denied` or `command not found`; it must be `pixi run -- cargo …`.
- `pixi run` tasks marked `depends-on = ["bun-install"]` (e.g. `version`, `version-check`) re-run
  the frozen Bun install first, so they are safe from a cold `node_modules`.

Do **not** run bare `cargo`, `bun`, `taplo`, `actionlint`, `convco`, or `clang-format`. Per-package
verbs live in each package's own `package.json` ([D10](/.knowledge/decisions/D10-xtask-over-shell-scripts.md))
and are fanned out by turbo — `pixi run` keeps the package directory as the working directory, so
those scripts need no `cd`.

### Regenerating the sandbox files is a ritual, not a command

`.github/workflows/publish-sandbox.yml` carries **local policy edits** that `init` does not produce
(the push-path filter, least-privilege permissions, concurrency, timeouts, pinned `pixi-version`,
and `cache: false` on every `setup-pixi` — see the comment block at the top of the file). Because of
that, `pixi sandbox init` **refuses** to overwrite the workflow once it is edited:

```console
$ pixi sandbox init --project-root . --script-path scripts/restore.sh
error: .github/workflows/publish-sandbox.yml has local modifications; refusing to overwrite
```

So regeneration means: `git rm` the three generated files, install the pinned release from
`https://prefix.dev/archont561/archont561` + `conda-forge`, re-run `init`, then re-apply the five
edits and read the diff to confirm those were the only changes. Track the diff; do not trust that the
ritual was faithful. `pixi sandbox init` in 0.5.0 leaves `pixi.toml`'s 241 comment lines alone, so
there is no `git checkout pixi.toml` step (that was fixed upstream).

### Known limits of this machine

- **`gh` is not installed.** Use `curl` against the API. Both available credentials are GitHub App
  tokens: `$GITHUB_TOKEN` and the codespaces `git credential fill` value. Both are scoped
  `issues=read` / `metadata=read`, so **creating issues, comments, PRs and workflow dispatches
  returns `403 Resource not accessible by integration`** — hand the user the title and body to post
  instead. Reads and `git push` do work.
- Get a push credential without writing git config: it already comes from the codespaces helper
  `/.codespaces/bin/gitcredential_github.sh`; `git credential fill` with `protocol=https` and
  `host=github.com` returns it.
- QGIS tests need `QT_QPA_PLATFORM=offscreen` and `--test-threads=1`; the pixi tasks already set
  both, and `pixi run setup` is the one-time libqca link fix.

## 2. Survey the backlog

1. **Sync before proposing.** `git fetch origin`, then confirm the working branch is based on
   `origin/main`'s tip — if it is behind, say so before anything else. Never edit on a stale base.
2. **Read the standing context** (skim, do not quote back): `AGENTS.md` (repo map, invariants, test
   layout), `CONTEXT.md` (orientation), and `.knowledge/decisions/` — **D01–D11 are load-bearing**;
   if you think one is wrong, bring a measurement, not an opinion.
3. **List the open work**: `pixi run backlog task list --plain` (27 To Do, 1 In Progress as of
   2026-10-03), or read `backlog/tasks/*.md` directly. A task file's frontmatter carries
   `dependencies`, `priority`, `ordinal`, `type`; spec docs live in `backlog/docs/`.
4. **Filter honestly.** A task is a candidate only when every dependency is `Done`. Order candidates
   by priority (high → low), then `ordinal`. A spike that unblocks several tasks may jump the queue
   — say so explicitly when you propose it.
5. **Do not re-propose finished work.** Check `git log --oneline -15`, recently merged PRs, and the
   latest release tag. Done tasks, merged decisions, and published releases stay done.

Do not hand-edit task metadata when the CLI can change it — go through the backlog skill so IDs,
dependencies, acceptance criteria and status stay consistent.

## 3. Propose the session, then stop

Fill in the **Session standup** (template §2) in [`standup-template.md`](standup-template.md) and
**wait for the user to pick** — do not start implementing.

That file carries all four phases of the lifecycle, and a session is only closed when every one of
them has been produced: the **opening prompt** (template §1) that started this session, the
**standup** (template §2) you are writing now, a **task hand-off** (template §3) at the end of each
task, and the **session report** (template §4) after the merge — which ends by emitting the next
opening prompt.

## 4. While you work — house rules (`AGENTS.md` is the full list)

- **One focused conventional commit per task.** The hooks are split by cost, so match your rhythm:
  - while committing: `pixi run format-cpp` plus the Rust and JSON formatters. `pre-commit` runs
    rustfmt, clippy, clang-format, taplo, actionlint and biome over **staged files only** — no
    cargo build, by design.
  - before pushing: `pre-push` runs the gate. Run `pixi run gates` yourself first when you want the
    answer sooner, or when the change touches what only the full `ci` covers (coverage producers,
    `pack:check`).
  - message check: `pixi run lint-commit` is what the commit-msg hook runs.
- **Tests live in `tests/`, never in `src/`** ([D11](/.knowledge/decisions/D11-tests-outside-src.md)).
  No `#[cfg(test)] mod tests` blocks. An integration test that needs an item makes it **public**,
  with a doc comment saying the test is why. Integration tests use the crate the way any consumer
  would.
- **Automation is a crate, not a script** ([D10](/.knowledge/decisions/D10-xtask-over-shell-scripts.md)):
  add an `xtask` subcommand with a unit test rather than a `scripts/*.sh`. If a change makes a
  source file invisible to git, `pixi run xtask check-sources` fails the gate — `.gitignore`
  ignores `.*` and `_*`, which once swallowed the whole Python client.
- **Complete the task file in its own format**: every AC `[x]`, status `Done`, bump `updated_date`,
  append Implementation Notes and Final Summary — following the task's existing section markers (no
  PLAN edits).
- **Tests target fixtures and tempdirs**, never this repository or a real `HOME`.
- **QGIS is not thread-safe**: no `Send`/`Sync` on wrappers, no sharing across threads, clone data
  before handing it to a worker.
- **Pull requests**: push the working branch, squash-merge, conventional title ending `(#N)`. Watch
  the required checks; when a platform job fails, read that job's log before changing code. What
  happens after the merge is §5, not an afterthought.

## 5. After the work lands on main — report, then hand the next session its prompt

A merge is not the end of a session; it is the first moment you can tell the truth about it. The
close is the same whether the work arrived by squash-merge or by a direct push to `main` (a release
fix, an amend into the release commit, a tag move — §5 step 1 covers the runs either way; the report
says `Merged: PR #N …` or `Pushed straight to main at <sha>`). Do these in order, and do not skip to
the report:

1. **Watch the post-merge runs.** List them (`gh run list --branch main --limit 5` if `gh` exists,
   otherwise the Actions tab, or `curl` `…/repos/Archont561/qgis-rs/actions/runs?branch=main`) and
   read the verdict of every workflow the merge triggered: `ci`, `docs`, and — on a push that
   touches a sandbox input — **`publish sandbox`**, which repacks the transport; also `relock` and
   `autorelease` on a release commit. A red post-merge run belongs to **this** session — fix it
   before reporting, never leave it as the next session's surprise. Job logs are fetchable with
   `curl …/repos/Archont561/qgis-rs/actions/jobs/<id>/logs`.
2. **Close the task files** in house format — in the pull request itself when the evidence is
   already in hand, in a follow-up commit when the proof only arrives after the merge: every AC
   `[x]`, status `Done`, `updated_date` bumped, Implementation Notes and Final Summary appended, no
   PLAN edits. **An AC you could not prove is not a checked AC.** When the remaining proof needs a
   native runner, a cut release or a maintainer's click, leave the task `In Progress`, name the AC
   and the missing proof in the notes, and carry that same sentence into the report.
3. **Re-baseline on the merged tree.** `git fetch origin && git log --oneline origin/main -1` to
   confirm what merged, then `pixi run gates`. The number goes in the report and into the next
   opening prompt; it must rise with new work, never fall. The last recorded baseline is **132 Rust
   tests across 29 integration test files**, plus **42 bun tests in `qgis-sdk`** and **42 in
   `qgis-rs`** (2026-10-03).
4. **Record what you did not implement** in [`.knowledge/log.md`](/.knowledge/log.md) under a dated
   heading, newest last, and end that entry with the next session's opening prompt, so the file in
   the tree and the message in the chat say the same thing. Proposals, alternatives weighed, and
   measurements worth keeping belong in the log — never in the files they speculate about. That
   entry is its own commit (`docs(log): …`), so the repository carries its own session summary.
5. **Print both artifacts in the final message**: the **Session report** (template §4) and, inside
   it, the **Session opening prompt** (template §1). Printing them *is* the hand-off. The test is
   literal: the user should be able to paste that prompt back as the first message of the next
   session and have an agent reach the same understanding you have now, without reading the diff.

A session that merged nothing still reports — "Merged: nothing", the ideas in the log, and an opening
prompt that says what to decide first.
