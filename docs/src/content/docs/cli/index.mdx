# qgis-cli

The `qgis-cli` binary provides command-line access to qgis-rs rendering and serving capabilities.

## Commands

| Command | Description |
|---------|-------------|
| `version` | Report CLI, engine, transport, target and backend versions |
| `capabilities` | Discover operation availability and domain limits |
| `doctor` | Diagnose pure-engine readiness and optional QGIS support |
| `validate` | Validate extents, CRS syntax, zoom ranges and XYZ tiles |
| `inspect` | Inspect project file metadata only, without parsing or validation |
| [`plan`](/cli/tiles#planning-without-a-project) | Count deterministic work from input alone, without a project or QGIS |
| [`render`](/cli/render) | Render a QGIS project to an image |
| [`tiles`](/cli/tiles) | Generate tile pyramids |
| [`batch`](/cli/batch) | Batch render multiple extents |
| [`info`](/cli/info) | Inspect a QGIS project |
| [`serve`](/cli/serve) | Start an HTTP map server |
| [`export`](/cli/export) | Export features from a layer |
| [`mcp`](/cli/mcp) | Serve the same capabilities as an MCP server for AI assistants |

:::note
`qgis-cli` is the command-line front end for the `qgis-render` and
`qgis-server` crates. Each subcommand maps onto a module in the
[API Reference](/reference/) — `render` onto [`render`](/reference/render),
`tiles` onto [`tiles`](/reference/tiles), `export` onto
[`features`](/reference/features), and `serve` onto
[`server`](/reference/server).
:::

## Discovery

```bash
qgis-cli version --json
qgis-cli capabilities --json
qgis-cli doctor --json
```

These read-only commands share a report containing `cli` (name and version),
`target` (OS and architecture), `engine` (version, transport version, backend,
limits and operation availability), `commands`, `command_note`, `status` and
`diagnosis`. Omit `--json` for human-readable output. The existing `--version`
flag still prints only the CLI name and version.

`commands` describes the parser surface, **not execution availability**.
`engine.operations` lists the protocol vocabulary with an `available` boolean
and a `reason` for unavailable routes. Native manager support alone does not
make an unimplemented engine route or CLI command available. In particular,
these discovery commands do not change the existing render/export/serve gates.

The backend report distinguishes `compiled` from live `available`, includes
`qgis_version` when available, and retains the backend `error` on failure.
Native builds probe through the manager's owner thread; pure builds do not load
QGIS. Reported limits are the enforced zoom and latitude domain limits, not
promises of worker, memory or cancellation controls.

For a pure Rust build, with no QGIS, Qt, Python, Node or WebEngine dependency:

```bash
cargo build -p qgis-cli --no-default-features
```

Successful reports exit **0**, including `doctor` when the optional backend is
absent and the pure engine is healthy. Argument errors exit **2** with diagnostics
on stderr. JSON stdout contains only the report; native-library diagnostics may
appear on stderr. Reports are deterministic for the same build and runtime
state and perform no implicit downloads or artifact writes.

`doctor` explains build/runtime requirements; it does not install dependencies,
scan profiles, or guarantee that a particular project/provider will work.
Project-manifest inspection, additional validation types and resource policies
remain later TASK-41 slices. Pure tile and CSV batch planning are available
under `plan`; they do not make the legacy rendering commands available.

## Validation

```bash
qgis-cli validate extent "14,50,15,51" --json
qgis-cli validate crs "epsg:4326" --json
qgis-cli validate zoom "10-14" --json
qgis-cli validate tile "10/551/340" --json
# Use -- before values beginning with a minus; put flags before --:
qgis-cli validate --json extent -- "-180,-90,180,90"
```

Validation uses only pure Rust domain types, even in a native-enabled build.
It does not load a backend, write artifacts/configuration, or access the network.

- **extent**: four finite, ordered coordinates. Zero-width and zero-height
  extents remain valid, matching the existing domain type. These are generic
  coordinates, not necessarily longitude/latitude.
- **crs**: authority-code syntax and case normalization only. The normalized
  value includes `validation: "syntax_only"`; success does **not** establish
  that the identifier exists in a CRS database or supports transformations.
- **zoom**: a single level or inclusive ordered range within 0–22.
- **tile**: unsigned `z/x/y` coordinates, with a supported zoom and indices
  strictly below the number of tiles per side. Invalid indices are rejected,
  never clamped. The normalized value includes the tile and EPSG:4326 bounds.

All JSON reports contain `kind`, `valid`, `value`, and `error`. Valid inputs
exit **0**, with a normalized value and `error: null`. Invalid domain inputs
exit **10**, with `value: null` and an error containing `code: "invalid_input"`
and `message`. The diagnostic is also written to stderr, never mixed into JSON
stdout. Reports are deterministic for the same input/build.

Missing arguments, unknown kinds, and invalid options exit **2**, produce no
JSON report, and write usage diagnostics to stderr. Omit `--json` for a readable
success report; human-mode domain failures write only to stderr. This new exit
mapping applies only to `validate`; legacy commands keep their existing exits.

Render settings, output-format validation, batch manifests, and operation
requests are not part of this slice. Use `validate --help` for the supported
kinds rather than interpreting discovery's engine operation list as validators.

## Metadata-only project inspection

```bash
qgis-cli inspect map.qgs --json
qgis-cli inspect "maps/city project.QGZ"
# Put flags before -- when the path starts with a minus:
qgis-cli inspect --json -- -map.qgs
```

`inspect` reads **filesystem metadata only**. It does not read file contents,
parse XML, inspect ZIP entries, validate CRS/layers, or initialize QGIS—even
in a native-enabled build. Success means metadata was obtained from a supported
regular file, **not that the project is valid**. Empty files, malformed XML and
non-ZIP bytes with a `.qgz` name can all return success. A native-enabled binary
still has its native shared-library dependencies; use the pure build described
above when those libraries are absent.

For a seven-byte file containing `<qgis/>`, the JSON report is:

```json
{
  "inspection": "file_metadata",
  "qgis_validation": "not_performed",
  "value": {"path": "map.qgs", "format": "qgs", "size_bytes": 7},
  "error": null
}
```

- Format comes from the supplied path's `.qgs` or `.qgz` extension,
  case-insensitively, not from its contents or a symlink target's name.
- Paths are reported as supplied, without canonicalization. Spaces and Unicode
  are supported. Non-UTF-8 paths are rejected rather than serialized lossily.
- Symlinks are followed: regular targets are accepted, directory/special-file
  targets are rejected, and dangling targets count as missing input.
- Filesystem metadata is checked before file type, extension and UTF-8 checks.
  Symlink loops, permission errors and other stat failures are filesystem errors.
- The command writes no artifacts or configuration and performs no implicit
  network requests or provider access. It does not prohibit an OS-managed
  network filesystem or a symlink target outside the current directory.

| Exit | Meaning | JSON error code |
|------|---------|-----------------|
| 0 | Metadata inspection succeeded | `error: null` |
| 2 | Missing/extra arguments or invalid options | No JSON report; usage on stderr |
| 10 | Unsupported extension, non-regular file, or non-UTF-8 path | `invalid_input` |
| 11 | Missing file or dangling symlink | `missing_input` |
| 14 | Other filesystem metadata failure | `filesystem_failure` |

For inspection failures, `value` is `null`; `error` contains `code` and `message`.
The scope/validation markers remain present, and diagnostics also go to stderr.
JSON stdout contains only one report. Reports are deterministic for unchanged
input, filesystem and runtime state; filesystem diagnostic text can vary by OS.
Omit `--json` for readable metadata and explicit inspection limits; human-mode
failures write only to stderr.

Legacy `info` remains separate, with its existing report, flags and exits.
No engine operation or FFI contract changes are implied by the new CLI command.
XML/container manifests, declared project metadata, native validation,
atomic artifacts, cancellation and resource limits remain later TASK-41 slices.

## Deterministic tile planning

```bash
qgis-cli plan tiles --bounds 14,50,15,51 --zoom 10-14
qgis-cli plan tiles -b 14,50,15,51 -z 10-14 --json
```

`plan tiles` counts an XYZ pyramid over an EPSG:4326 extent. It is pure
geometry: it takes no project argument, opens no file, initializes no backend,
and writes nothing. That is what separates it from `tiles <project> --dry-run`,
which counts the same numbers but opens a `.qgs`/`.qgz` first.

The report is the same shape the engine's `plan_tiles` operation and the MCP
`plan_tiles` tool return — `bounds`, `zooms`, `tile_count` and one `levels`
entry per zoom level, each carrying its own `tile_count`. One definition in
`qgis-render`, three surfaces, so they cannot disagree:

```json
{
  "bounds": { "min_x": 14.0, "min_y": 50.0, "max_x": 15.0, "max_y": 51.0 },
  "zooms": { "min": 10, "max": 14 },
  "tile_count": 4568,
  "levels": [
    { "zoom": 10, "x_min": 551, "x_max": 554, "y_min": 342, "y_max": 347, "tile_count": 24 }
  ]
}
```

| Exit | Meaning |
|------|---------|
| 0 | Planning succeeded |
| 2 | Missing/extra arguments or invalid options; usage on stderr |
| 10 | Unreadable `--bounds` or `--zoom`, or an unordered extent/zoom range |

Exit **10** is the same category `validate` uses, so malformed input means the
same thing whichever pure command refused it. Legacy commands keep their
existing exits. With `--json`, a failure still leaves one parseable document on
stdout — an `error` object with `code: "invalid_input"` and `message` — and the
diagnostic also goes to stderr. Omit `--json` for one row per zoom level plus
the total.

Planning does not decide whether the tiles can be *rendered*: output formats,
storage backends, native execution gates, cancellation and resource limits
are not part of this command.

## Deterministic CSV batch planning

```bash
qgis-cli plan batch --extents extents.csv --zoom 10-14 --json
```

[`plan batch`](/cli/batch) reads the existing `name,minx,miny,maxx,maxy` CSV
vocabulary and embeds the same `TilePlanReport` for every row. It takes no
project or output argument, initializes no backend and writes nothing. The
report contains `extent_count`, summed `tile_count`, and ordered `extents`
entries with `name` and `plan`. Duplicate/overlapping rows are counted
separately, and empty input produces a zero-work plan.

Exits are **0** success, **2** usage, **10** invalid input, **11** missing CSV
and **14** filesystem failure. JSON failures contain one `error` object and
no partial plans; diagnostics also go to stderr. The CSV is not quoted-field
RFC CSV or GeoJSON. No engine operation or FFI wire shape is added, and the
legacy `batch <project>` command keeps its flags and rendering gate.

## Installation

```bash
cargo install qgis-cli
```

Or build from source:

```bash
cargo build --release -p qgis-cli
```

## Quick Examples

```bash
# Render a project
qgis-cli render map.qgs -o map.png

# Generate tiles
qgis-cli tiles map.qgs -z 10-14 -b 14,50,15,51 -o ./tiles/

# Start a server
qgis-cli serve map.qgs --port 8080

# Inspect a project
qgis-cli info map.qgs

# Serve the same capabilities to an MCP client over stdio
qgis-cli mcp
```
