# Batch planning and rendering

## Pure planning: `qgis-cli plan batch`

```bash
qgis-cli plan batch --extents extents.csv --zoom 10-14
qgis-cli plan batch --extents extents.csv -z 10 --json
```

Planning takes **no project or output argument**. It reads filesystem metadata
and the supplied UTF-8 CSV, computes one XYZ pyramid per named EPSG:4326 extent,
and initializes no backend. It does not render, create directories, write
artifacts or configuration, or invoke Python, Node or WebEngine. Native-enabled
builds still need their shared libraries; use `--no-default-features` for an
independent pure Rust binary.

| Option | Required | Description |
|--------|----------|-------------|
| `--extents <FILE>` | Yes | UTF-8 `name,minx,miny,maxx,maxy` CSV. |
| `-z, --zoom <RANGE>` | Yes | One level or inclusive range within 0–22, shared by every extent. |
| `--json` | No | One deterministic JSON report instead of readable text. |

### CSV vocabulary

The existing batch CSV parser is reused, not replaced with a second parser:

```csv
name,minx,miny,maxx,maxy
central,14,50,15,51
```

- Input order, Unicode names and duplicate names are preserved. Names are
  labels, **not validated output paths**.
- Blank lines and lines beginning with `#` after trimming are skipped.
- A row whose first field is `name`, case-insensitively, is skipped wherever
  it appears. Surrounding field whitespace is trimmed.
- Four finite, ordered numeric coordinates are required after the name.
  Additional columns are ignored, matching legacy behavior. This is a simple
  comma-separated format, not quoted-field RFC CSV or GeoJSON.
- Empty and header/comment-only files are valid zero-work plans.
- Every row uses the same tile-domain rules as `plan tiles`; there is no new
  CRS lookup, coordinate transformation or native validation.

### Reports

With the CSV above and `--zoom 10`, the complete JSON report is:

```json
{
  "extent_count": 1,
  "tile_count": 24,
  "extents": [
    {
      "name": "central",
      "plan": {
        "bounds": {"min_x": 14.0, "min_y": 50.0, "max_x": 15.0, "max_y": 51.0},
        "zooms": {"min": 10, "max": 10},
        "tile_count": 24,
        "levels": [
          {"zoom": 10, "x_min": 551, "x_max": 554, "y_min": 342, "y_max": 347, "tile_count": 24}
        ]
      }
    }
  ]
}
```

Each `plan` is the existing `qgis_render::TilePlanReport`, also emitted by the
engine, MCP and [`plan tiles`](/cli/#deterministic-tile-planning). No new engine
operation or FFI wire shape is introduced. Counts are computed without
enumerating tiles. The top-level `tile_count` sums the rows; overlapping or
repeated extents are counted separately, not deduplicated.

Without `--json`, the same example prints:

```text
central: 24 tiles across zoom levels 10-10
24 tiles across 1 extents
```

### Failures and filesystem scope

| Exit | Meaning | JSON error code |
|------|---------|-----------------|
| 0 | Planning succeeded, including a zero-work plan | No error field |
| 2 | Missing arguments, extra project/output arguments, or invalid options | No JSON; usage on stderr |
| 10 | Invalid zoom, malformed/non-finite/unordered CSV coordinates, non-UTF-8 contents, or a non-regular input | `invalid_input` |
| 11 | Missing CSV or dangling symlink | `missing_input` |
| 14 | Other filesystem metadata/read failure, including a symlink loop | `filesystem_failure` |

A failed plan emits no partial extents. With `--json`, stdout contains only
`{"error":{"code":"…","message":"…"}}`; the diagnostic also goes to stderr.
Human-mode failures write only to stderr. CSV syntax errors retain the existing
parser's line number. Zoom validation precedes filesystem access.

Symlinks to regular files are followed. There is no new path-containment policy,
input-size/memory/worker limit or cancellation contract. Output paths, native
renderability, XML/container inspection and atomic artifact policy remain
separate work. A successful plan is not a promise that the batch can be rendered.

## Legacy rendering: `qgis-cli batch <PROJECT>`

The existing command and its flags remain separate and unchanged:

```bash
qgis-cli batch map.qgs --extents extents.csv --output ./renders/ [--zoom 10]
```

| Option | Description |
|--------|-------------|
| `<PROJECT>` | Required `.qgs` or `.qgz` project path. |
| `--extents <FILE>` | Required CSV with the vocabulary described above. |
| `-o, --output <DIR>` | Required target directory argument. |
| `-z, --zoom <VALUE>` | Existing optional argument; the gated renderer does not use it yet. |

This command opens the project first, reads and reports the extents, and then
fails with the existing batch-rendering backend diagnostic and exit **1**. It
currently writes no renders. GeoJSON input, image-size/format/worker flags,
per-extent retry behavior and a working batch renderer are not implemented.
Use `plan batch` when only a project-independent work estimate is required.
